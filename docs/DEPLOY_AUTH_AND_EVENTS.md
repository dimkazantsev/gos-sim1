## 2. Установка личного пароля

Вход по исходному игровому коду остаётся доступным. Для повторного входа с другого устройства студент или преподаватель открывает собственный игровой профиль и привязывает **свой** адрес электронной почты. После подтверждения адреса в профиле устанавливается пароль длиной не менее 10 символов. При последующем входе используйте вкладку «Войти с личным паролем», укажите код игры, почту и пароль. Все игровые данные остаются у той же записи пользователя после корректной конвертации Supabase Auth.

Перед использованием необходимо проверить в **Supabase Dashboard → Authentication**:

- Включены **Anonymous Sign-Ins**, **Email** и **Allow manual linking** (привязка идентичности анонимного пользователя). Эта опция настраивается на уровне Supabase Auth, а не миграцией SQL.
- **Site URL** и **Redirect URLs** включают официальный адрес сайта и `https://ваш-домен/auth/update-password`. Для тестирования добавьте соответствующий адрес тестового окружения.
- Работает **Custom SMTP** для массовой рассылки писем о подтверждении и сбросе; тестовый отправитель Supabase ограничен и не предназначен для полноценного занятия.
- Проверены подтверждение почты, установка пароля, выход/вход с другого устройства и восстановление доступа на тестовой учётной записи.

Преподаватель может отправить студенту ссылку для сброса пароля из собственного профиля, если студент уже привязал подтверждённую почту. Преподаватель не может увидеть старые пароли; хеши хранятся в Supabase Auth. Запрещено публиковать service-role / secret key в клиентском коде.

## 3. Автоматический сценарий

В преподавательском разделе **Event → Автоматический сценарий** выберите базовый интервал (4–72 часа), интенсивность учёта активности, дневной предел 1–3 назначения и параметры влияния на доверие. Сохраните настройки, затем включите автоматический запуск. По умолчанию сценарий **остановлен**. При активном режиме задание в `pg_cron` проверяет все включённые игры один раз в час.

Формула эффективного интервала в часах:

`I = max(4, base_interval / (1 + activity_weight * min(2, idle_hours / 48)))`.

Для каждого студента действуют одновременно три ограничения:

1. Не более установленного количества автоматических назначений за последние 24 часа (1–3).
2. Не более трёх незавершённых заданий одновременно.
3. Один банковский кейс не назначается одному и тому же студенту повторно.

Банк пока содержит **12 уникальных авторских вымышленных кейсов** в каждой игре, а не 500 проверенных исторических ситуаций. Кейсы группируются по должности и степени серьёзности; неактивным студентам чаще назначаются лёгкие / необычные ситуации. Преподаватель может назначать ситуации вручную и добавлять собственные задания.

Каждые 20 обработанных участниками ситуаций повышают **игровой показатель «Доверие граждан»** на установленную величину, по умолчанию на 2 процентных пункта. Каждый день за каждые три просроченные более чем на 48 часов ситуации рейтинг понижается на установленное число пунктов, но суммарно не более чем на 3 пункта в сутки. Учёт ведётся через `event_trust_ledger` и `state_metric_history`, повторные начисления защищены уникальным ключом. Это сценарная игровая модель, не статистический прогноз.

## 4. Фото и подписи

Фото профиля изменяется через круглую иконку камеры; описание ограничено 350 символами. Для подписи загрузите фото тёмной подписи на ровном белом листе. Браузер обрежет пустые поля, удалит светлый фон и покажет прозрачный PNG перед подтверждением. Запись реального действия подписания НПА создаёт в `formal_document_signatures` отдельный снимок пути к изображению, действовавшему на этот момент. Новые подписи не заменяют ранее зарегистрированные подписи на документах. До первого подписанного документа изображение подписи доступно только владельцу и преподавателю. Подписи служат **исключительно оформлению учебных документов**, а не юридически значимой электронной подписью.

## 5. Контрольный прогон до занятия

1. Преподаватель проверяет отображение этапов и чата на широком и узком экранах, перемещение по разделам и центровку элементов.
2. На тестовом студенте проверяет доступ к личному и чужому профилю, приватность текстовых доказательств оценки, фото, подпись, подтверждение почты, вход и восстановление.
3. Для событий запускает автосценарий вручную, проверяет уникальные назначения, дневной лимит, роль адресата, паузу, статистику Да / Нет и журнал доверия.
4. Создаёт тестовый НПА, проходит фактическую процедуру подписания, сравнивает имя, дату и сохранённый снимок подписи, затем меняет подпись профиля и проверяет неизменность старого документа.
5. Проверяет приложение после фактического развёртывания Vercel: успешная сборка GitHub Actions сама по себе не доказывает доступность публичного сайта.

**Примечание:** тестовая отправка писем, вход с другого устройства, доступ к реальной камере и многопользовательская проверка должны выполняться с действующими тестовыми пользователями на целевом домене. Браузерные CI-тесты исходного интерфейса не заменяют эти проверки.
