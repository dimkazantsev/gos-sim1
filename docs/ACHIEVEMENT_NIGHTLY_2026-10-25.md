# Ночное обновление достижений

Решение владельца от 25 октября 2026 года: расчёт достижений перенесён на 03:00–04:00 по Новосибирску. Днём участники читают готовые результаты. Уже полученные награды, даты получения и уведомления сохраняются; награды не меняют ВСН.

Причина подтверждена рабочим журналом: 25 октября в 10:55:37 UTC вычисление `achievement_facts` внутри `evaluate_game_achievements` отменено по тайм-ауту `57014`. Аналогичные тайм-ауты были в присутствии, комитетах и Realtime, поэтому исправление наград не доказывает устойчивость всего приложения.

## Сервер

`private.achievement_snapshots` хранит факты и дату успешного расчёта отдельно для каждой пары игра/участник. RLS включён, прямые права клиентов отозваны. Дневной `get_game_achievements` читает этот снимок с прежней проверкой членства и текущими настройками скрытых наград. До первого расчёта показываются существующие награды, остальной прогресс равен нулю с пояснением в интерфейсе. Старый `evaluate_game_achievements` оставлен совместимым быстрым вызовом без вычисления фактов.

Одна задача Supabase Cron обрабатывает одного действующего студента за запуск, включая отсутствующих в браузере. Учителя, наблюдатели и архивные участники исключены. Запуски идут в 03:01–03:59, кроме минут 11, 31 и 51, занятых существующими часовыми задачами. В базе используется GMT: расписание `1-10,12-30,32-50,52-59 20 * * *` соответствует этому окну в Новосибирске следующего дня. Глобальная транзакционная блокировка исключает параллельные расчёты наград. Команда ограничена 15 секундами; участнику разрешены три попытки за ночь с паузой не менее пяти минут. При ошибке сохраняется прежний успешный снимок и закрытый SQLSTATE ошибки.

Граница ёмкости — **56 обработок на весь проект за ночь**, включая повторные попытки. Для 40 участников остаются 16 резервных попыток. Перед применением в рабочей базе было два действующих студента; число не подменялось 40 тестовыми записями. При росте общего числа участников или длительности вычислений нужен повторный замер и пересмотр размера партии. Одного расписания недостаточно для гарантии выполнения при любом сбое провайдера.

Накопительный учёт присутствия сохранён, календарные дни его правил остаются в UTC. Новые награды за лидерство и действующие должности оцениваются по состоянию ночного расчёта; уже выданные достижения не отзываются.

## Клиент

Постоянные интервалы и клиентский вызов расчёта удалены. Полка читает готовые результаты при открытии профиля, затем один раз после 04:00 с разбросом 15–60 секунд. Скрытая вкладка ждёт возвращения пользователя. Уведомление проверяет только готовую награду один раз за расчётный день для пользователя и игры. В хранилище браузера остаётся только дата попытки, без содержимого наград. Смена профиля и выход очищают старые результаты; поздний ответ не отображается в новом профиле. Ошибка необязательного уведомления не перекрывает управление игрой.

## Проверка и бюджет

Самодостаточные проверки: `node scripts/achievement-nightly-client-check.cjs`, `node scripts/achievement-nightly-database-check.cjs`, `node scripts/achievement-preview-check.cjs`.

Изолированная проверка реальных эффектов компонента: 40 независимых клиентов, 20 виртуальных минут. Для раскрытой полки исходный main `5c39448deedfabe919111d0fb0377df6bbb7d365` отправил 938 RPC, кандидат — 120 начальных RPC, затем ноль повторных дневных запросов наград. Без профиля: 618 → 40. Это модель с тестовыми ответами, без реального Auth, WebSockets, HTTP-задержек и серверного p95. На тестовом наборе JSON ответов раскрытой полки: 2 384 672 → 595 800 байт; сжатие и HTTP не измерялись. Дневные чтения и совместимый evaluate в PGlite вызывают факты ноль раз. 40 ночных синтетических студентов обрабатываются ровно 40 вычислениями; 4000 наград в тесте означают намеренно выполненные все 100 условий, а не реальные достижения.

Рабочая проверка после миграции `20261025124344`: дневной обработчик возвращает 0; оба дневных RPC не вызывают `achievement_facts`; клиентский доступ к снимкам и ночному обработчику закрыт; единственный cron активен. Число существующих наград 27 и контрольная сумма их строк до/после совпали. Первый ночной расчёт ожидается 26 октября в 03:01–04:00 по Новосибирску; его фактическое завершение ещё не проверено.

Новая работа выполняется внутри существующей базы: дополнительных Vercel Functions, HTTP-вызовов и аналитических событий нет. Management API показывает существующий план организации Pro; тариф и платные дополнения не изменялись. Остаток общей квоты трафика/вычислений и дата её обновления через доступные инструменты не получены, поэтому массовый тест рабочей базы не запускался. Размер базы перед изменением — 106 187 923 байта. Абсолютная гарантия отсутствия перегрузки при внешней квоте не заявляется.

Визуальная проверка ограничена: локальная страница не открылась во встроенном браузере; Computer Use затем остановил управление, поскольку не смог надёжно определить адрес в Windows. Обход не применялся. Новые снимки экрана, физические устройства и реальные 40 сеансов по 20 минут не проверены. Полный SQL интеграции требует отдельной изолированной схемы и в production не запускался.

Основание расписания и ограничений: [Supabase Cron](https://supabase.com/docs/guides/cron), [pg_cron](https://github.com/citusdata/pg_cron), [официальные тарифы](https://supabase.com/pricing). Изучены через Context7 и официальные страницы. PostHog содержит только проект без поступавших событий; телеметрия ГОС.ID там не подтверждена. MagicPath не содержит макетов ГОС.ID; новое оформление и параллельный сайт Sites для исправления серверной нагрузки не создавались.
