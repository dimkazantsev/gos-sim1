# ГОС.ID — задача #491, итерация 1. 100 самостоятельных JWT при голосовании

## Неизменяемые условия

Правила игры, оценки, дизайн, опубликованные голосования, продуктивные RLS/RPC, миграции, Supabase и его ключи не изменяются. Проверка работает **исключительно в одноразовом локальном Supabase в GitHub Actions**. Строгая проверка loopback URL и метки пустой базы исключает подключение к удалённой базе. Тест запускается только при изменении соответствующего сценария, workflow или ранее существующего генератора SQL фикстуры.

## Зачем дополнительный тест

Предшествующий тест `ballot-isolated-100.yml` уже проверяет 40/100 конкурентных соединений непосредственно с PostgreSQL и тела производственных функций голосования, автоматического закрытия и защиты от повторов, но **не** проходит цепочку Auth → JWT → PostgREST → RPC. Тесты 100 отдельных JWT для приватного Realtime в PR #490 проверяли другую подсистему и не повторяются.

Эта итерация проверяет реальную цепочку Auth/JWT → HTTP RPC → SQL для 100 отдельных тестовых аккаунтов. Она повторно использует существующий генератор изолированной схемы и действующие тела серверных функций. Схема голосования, членство, избирательный список и другие зависимости **умышленно упрощены**, как в прежней PostgreSQL-фикстуре; это не полная имитация производственной базы или 16 этапов игры.

## Сценарии и критерии

1. Пустой локальный Supabase, 100 самостоятельных JWT студентов, JWT преподавателя, гостя, постороннего пользователя; анонимная попытка.
2. Проверить серверные запреты постороннему, гостю без голосующего мандата, анонимному участнику и студенту, пытающемуся закрыть процедуру; прямое чтение закрытой таблицы бюллетеней запрещено.
3. Одновременно отправить 100 HTTP RPC с разными JWT и убедиться в 100 уникальных бюллетенях, правильном подсчёте и единственном закрытии голосования.
4. Отправить 30 одновременных повторов одного участника до закрытия — должна остаться одна запись. Остальные 99 бюллетеней должны привести к 100 уникальным записям.
5. Столкнуть 100 попыток голосовать с закрытием преподавателем. Принятые голоса не должны теряться, итог должен точно равняться подтверждённым записям; отклонения разрешены только вследствие уже закрытого голосования.
6. Напечатать машинно проверяемый JSON с задержками p50/p95/p99, принятыми попытками, отказами и границами испытания. После проверки полностью удалить одноразовую базу без резервных копий.

**Считать результат успешным только по GitHub Actions SUCCESS с отчётом.** Создание PR, его коммит, синтаксическая проверка или успешное поднятие локальной базы сами по себе не равны приёмке.

## Остающиеся ограничения

Это не 100 физических телефонов/браузеров и не весь продуктовый сценарий создания, уведомлений, документов и оценивания на всех 16 этапах. Сценарий использует подлинную функцию голосования, но упрощённые SQL-фикстуры членства и доступных голосов; невозможно объявить проверенными все реальные производственные RLS. Ещё требуются сквозные проверки UI и этапов в пределах задачи #491. Размеры передаваемых данных не выдаются за общий egress Supabase. Новые платные сервисы и обращения к продуктивной базе исключены.
