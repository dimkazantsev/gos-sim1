# ГОС.ID — утверждённая концепция событий V2
Дата решения: 27.11.2026. Владелец утвердил 10 положений в диалоге проекта ПАУ.
Статус: шаг 1 — спецификация и контроль исходных данных; НЕ включение новых игровых правил.

## Утверждено владельцем
1. Редактура всех 1660 вариантов ответа в 330 кейсах; устранить подсказку длиной, стилем и позицией.
2. Индивидуальные (141, 713 вариантов): один юридически и управленчески обоснованный лучший ответ.
3. Вместо приглашения — передача рассмотрения индивидуального кейса компетентному участнику. Государственная должность не передаётся.
4. За правильную передачу 0,5, за правильное решение переданного кейса 0,5, за прямое правильное решение 1. Балл за правильную передачу независим от результата исполнения; не увеличивать общий лимит знания закона за этап. Повторные действия не начисляют баллы.
5. Коллективные (30 group +159 all, 947 вариантов): не проверять полномочия голосующих и не изменять правовую устойчивость по коллективному выбору.
6. У коллективного решения нет скрытого единственного правильного ответа; все альтернативы юридически допустимы в конкретной процедуре.
7. Противоречивые политические и экономические эффекты, применяемые только к финальному решению один раз. Нельзя дублировать прямые и производные бюджетные эффекты модели V2.
8. Второй тур, когда первый не дал необходимого большинства.
9. Проверить реальные источники и применимость законодательства для каждого из 330 кейсов. URL или отметка автоматически не являются верификацией.
10. Сохранить историю, ранее выставленные баллы и результаты.

## Реализация: порядок и критерии завершения
Шаг 1. Спецификация, read-only preflight и границы совместимости (этот коммит).
Шаг 2. Индивидуальный кейс: реальный переход единственного активного назначения, журнал передачи, проверка компетенции и территории, исходный stage_no, оценка независимо от результата исполнителя. Проверить параллельную передачу/ответ, отказ, недоступность, дубли, архивную роль, другую игру, прежнюю историю.
Шаг 3. Коллективный кейс: отдельное правило оценки и второй тур; не создавать правовые оценки для голосов; без lawfulness и authority-trust бонуса; отсутствие лучшего ключа; один итог и один набор эффектов. Сохранить текущий порог строгого большинства от активного состава, отдельные голоса по турам, отсутствие автоматического принятия при равенстве. Зафиксировать состав и сроки; точные правила пограничных ничьих и сроков уточнить перед внедрением.
Шаг 4. Полная редактура 141 индивидуального и 189 коллективных сюжетов и всех 1660 ответов, точные полномочия, юридические/фактологические источники; сбалансировать длину, правдоподобие и позиции, отсутствие доминирующей альтернативы без объяснимой причины. Каждая цифра последствий — параметр игровой модели, не исторический факт; диапазоны согласовать с текущей экономикой.
Шаг 5. Интеграция, миграция и публикация: проверка всех ранее принятых решений, RLS, отсутствия ключа ответа до голосования, ролей, адаптивности, 100 имитируемых клиентов и целевых нагрузочных сценариев. Не объявлять реальные 100 клиентов испытанными по синтетическому тесту. Отчёт по каждому шагу: SHA, проверки, связи, оптимизация, айдентика, публикация.

## Совместимость и предложенные технические решения
- Хранить версию правил вместе с закрытым серверным планом эффектов (legacy по отсутствию маркера, V2 по явному маркеру). Не включать V2 до готовности всех обработчиков, UI и утверждённой редакции. Без дополнительного чтения за пределами уже загруженной строки кейса. Без передачи приватного effect_plan клиентам.
- При первом назначении фиксировать версию и содержание. Не переписывать назначенные кейсы и связанные записи. Для будущих игр редактура всех 330 ведётся отдельно от исторических экземпляров. Для 265 неиспользованных — безопасное обновление на месте при атомарной повторной проверке отсутствия связей. Для 7 открытых без голосов и 4 открытых с голосами по умолчанию сохранить V1; вопрос перевода 7 без голосов — отдельное согласование. Никакого ретроактивного перерасчёта 54 завершённых случаев.
- Серверный guard_event_assignment сейчас запрещает смену recipient_id; respond_event_invitation добавляет новое назначение. Нужна адресная атомарная процедура передачи с блокировкой кейса перед назначением, не ослаблять общий запрет.
- record_event_authority сейчас оценивает все голоса и меняет lawfulness один раз (+2/-3), а также trust при отсутствии нарушений. Для V2 group/all исключить эту ветку, сохранить остальные тематические эффекты.
- blitz_vsn_components сейчас даёт кейсам 0,30 * min(1, сумма score_share / количество оценённых кейсов); прочие компоненты 0,30 + 0,30 + 0,10. Доли 0,5/1 — сырой кредит кейса, а не добавка поверх лимита 1 за этап. Отдельная запись за передачу, без фиктивного голоса и без штрафа за последующую ошибку исполнителя. Связи: compute_vsn_assessment, достижения, проекция, обратная связь. Согласованное начисление коллективным кейсам не входит в правовую часть.
- finalize_game_case использует строгий порог > половины назначенных. Второй тур не должен писать исход первого тура в event_case_outcomes: иначе сработают фискальные, новостные и прочие триггеры. Ограничить максимумом двух туров; не удваивать права и последствия.
- Существующие приватные каналы, scoped invalidation и ленивый банк; никаких новых фоновых опросов, запросов ИИ, платных ресурсов. Использовать пакетную выдачу существующей проекции. Не расширять публичный доступ к ответам, полномочиям других игр или таблицам.
- Не изменять текущие цвета, типографику, размеры и компоновку. Использовать существующие компоненты.

## Проверка истории
scripts/events-v2-release-preflight.sql — только SELECT. Запуск до и после пробной миграции на изолированном наборе, в одной контролируемой транзакции: отпечатки защищённых кейсов/назначений/решений/итогов/оценок/приглашений должны совпасть для редакционной миграции. В действующей игре независимые новые голосования могут законно менять снимок, поэтому нельзя сравнивать суточные отпечатки как доказательство потери данных. Не хранить в GitHub идентификаторы, ФИО, тексты ответов участников или сырые дампы. Оценивать фактические результаты, а не обещать идеальность.

После готовности V2 перевести 7 открытых кейсов без голосов, если в момент релиза по ним всё ещё отсутствуют голоса и несовместимая история; 4 с голосами завершить по старым правилам. Механика шага 2 разрабатывается выключенной: кандидат SQL не применять отдельно, UI активируется публичным comic_scene.event_rules_version=2, сервер — приватным effect_plan.rules_version=2; согласованность маркеров обязательна на шаге 5. Передача только после согласия компетентного получателя; некомпетентному или при собственной компетенции передача отклоняется, назначение сохраняется. Отдельный кредит фиксируется на исходном этапе в принятой записи приглашения; один кейс — максимум одна такая передача. Существующий лимит В.С.Н. не изменён.
