# ГОС.ID — граница с QWIZ-PARTY, независимый backend
Проверка: 30 октября 2026. Статус: **подготовка; физическое разделение ещё не выполнено**.

## Факты

Основное приложение ГОС.ID размещено в `dimkazantsev/gos-sim1` (Next.js/Vercel). Рабочая PostgreSQL/Realtime/Auth/Storage база — Supabase `gos-sim` (`bderfrcfuhnutuoyudje`, eu-central-1, PostgreSQL 17.6).

Сейчас QWIZ-PARTY также использует этот же проект. Это означает общий пул вычислений и соединений, Realtime, Auth и суммарный расход ресурсов: **разные URL сайтов и префиксы таблиц не дают физической изоляции**.

Конфигурация ГОС.ID:
- `lib/supabase.ts`: берёт `NEXT_PUBLIC_SUPABASE_URL`, в противном случае использует прежний cloud URL; publishable key задаётся `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`.
- `public-client-config.json`: тот же текущий адрес (файл содержит legacy anon/public key; это не service_role и не должен становиться источником секретных credentials).
- Текущий production не менять, пока новый QWIZ backend не подтверждён.

## Обязательный план

**Сохраняем ГОС.ID в `gos-sim` без переноса.** QWIZ переводим на отдельный проект Supabase, отдельный ref и ключи. Только после подтверждения, что все QWIZ-клиенты ушли, можно проектировать удаление legacy QWIZ объектов в старой базе; удаление выполняется отдельной операцией, отдельно от cutover.

Были выполнены только безопасные read-only запросы к каталогам БД, без изменения ролей, функций, таблиц, cron, Auth или данных.

### Проверка возможных зависимостей от QWIZ

- Из 245 таблиц схемы `public` обособлены 36 `qwiz_*`, 5 `org_next_*`, 16 `org_quiz_*`.
- Среди foreign keys из **других** таблиц в эти семейства каталог `pg_constraint` не обнаружил ссылок; **это не подтверждает отсутствия** зависимостей в функциях, триггерах, динамических SQL, Edge Functions или коде приложения.
- **Два RPC с префиксом `org_party_*`** содержат текстовые ссылки на QWIZ-объекты: `org_party_create_set_from_questions` и `org_party_set_life_state`. До анализа владельца и предназначения их нельзя удалять ни из исходной базы, ни из нового клона.
- Всего в старом проекте 9 pg_cron job. Нет прямого совпадения с QWIZ по поиску `command ILIKE`, но косвенные зависимости не исключены.
- `game-assets`, `game-media` и `teacher-assets` заполнены; эти бакеты нельзя чистить исходя из названий. `org-party-media` сейчас пуст; даже при 0 файлах нужно проверить storage policies и ссылки.
- Edge Functions: `org-resolve-image` и `chat-media-cleanup` требуют отдельной классификации использования.

### Проверки после cutover

1. У ГОС.ID `NEXT_PUBLIC_SUPABASE_URL` и `public-client-config.json` указывают на `gos-sim`, а QWIZ на **другой** ref. Проверка `node scripts/verify-isolated-supabase.cjs` не допускает совпадение backend.
2. Вход преподавателя и студентов, роли, правила, приглашения, восстановление сеансов и операции голосования работают как до миграции.
3. Chat, media uploads, документы, ВСН, cron, Realtime и пользовательские файлы ГОС.ID не задействуют QWIZ endpoint.
4. Отдельно измерены p50/p95/p99 RPC и число ошибок при 40–100 участниках на ГОС.ID; изменение нагрузки **не гарантирует**, что каждый запрос станет быстрее.
5. Свежая статистика Supabase (Dashboard usage, Realtime, DB) не содержит клиентского трафика QWIZ после завершения окна устаревших вкладок / service workers.
6. Резервная копия исходной БД проверена на восстановление до каких-либо удалений.
7. Никакие `auth.users` исходного ГОС.ID не удаляются массово ради освобождения QWIZ; совпадающие преподавательские UUID и аккаунты требуют пообъектного анализа.

### Этапы физического разделения

A. Открыть отдельную организацию Supabase Free или согласовать платное создание проекта внутри текущей Pro организации; выбор организации делает пользователь.

B. Подготовить новый QWIZ только для тестовых данных. Не переносить таблицы ГОС.ID и его пользователей. Проверить функции, RLS/GRANT, Storage, Auth. Сопоставить реальный dataset, а не только названия.

C. После успешных регрессионных и нагрузочных тестов опубликовать новый адрес QWIZ и убедиться, что ГОС.ID продолжает обращаться к старому проекту.

D. Зафиксировать проверку целостности, независимые метрики, план отката и отдельную согласованную задачу на очистку старых объектов QWIZ.
